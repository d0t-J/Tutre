# Tutre — Supabase

This directory holds the Supabase CLI configuration for Tutre, plus the
migrations and Edge Function source once they are pulled from the hosted
project.

## Status

`config.toml` was generated by `supabase init` and is real.

`migrations/` and `functions/` are **not yet populated**. The hosted project
`belxamnldwfkagkmgobt` is currently the only source of truth for the schema, the
RLS policies, and the five Edge Functions. Pulling them requires credentials that
are not checked into this repository, so nothing here was reconstructed by hand —
a hand-written migration would be a guess, and a guess in `migrations/` is worse
than an empty directory.

Do not write migrations here from memory. Pull them.

## Pulling the real schema and functions

Requires two secrets, both obtained by the project owner:

1. A personal access token from <https://supabase.com/dashboard/account/tokens>
2. The database password for project `belxamnldwfkagkmgobt`
   (Dashboard → Project Settings → Database → Database password)

```bash
npx supabase login                                    # paste the access token
npx supabase link --project-ref belxamnldwfkagkmgobt  # prompts for the DB password
npx supabase db pull                                  # writes migrations/<timestamp>_remote_schema.sql
npx supabase functions download chat-tutor
npx supabase functions download generate-simulation-prompt
npx supabase functions download suggest-requirements
npx supabase functions download extract-html-details
npx supabase functions download send-whatsapp
```

`db pull` captures tables, columns, types, constraints, indexes, views, database
functions, and RLS policies. `functions download` captures Edge Function source.
Together they make this directory complete.

Alternatively, authorise the Supabase MCP server (type `/mcp` in an interactive
`claude` terminal) and the same reconstruction can be done from inside Claude
Code.

## Do not commit

`supabase/.env`, `supabase/.temp/`, and any file holding an access token, a
database password, a service-role key, or an AI provider key. The root
`.gitignore` and `supabase/.gitignore` already exclude these.

## What is known about the schema today

Everything below was verified against the live project, either by anonymous
PostgREST introspection or by reading the queries the two panels actually issue.
It is documentation, not a migration, and it is incomplete — types, nullability,
defaults, foreign keys, indexes, and every RLS policy are still unknown.

### Verified column lists

Read anonymously from PostgREST, so these column names and their order are exact.

**`chapters`**

```text
id, name, subject_id, created_at, chapter_no, description
```

**`all_simulations`** (a view, not a table)

```text
topic_id, topic, description, chapter_id, subject_id, subject, icon_name,
class_id, class_name, sim_id, code_payload, created_at, study_guide
```

### Tables that exist but are closed to anonymous reads

RLS returns zero rows for the anon role, so no columns could be read. Column
names below come from the frontend queries, and are therefore a partial list —
each table almost certainly has columns no query touches.

| Table | Columns referenced by the app |
| --- | --- |
| `classes` | `id`, `name` |
| `subjects` | `id`, `name`, `class_id` |
| `topics` | `id`, `name`, `subject_id`, `study_guide` |
| `admin_users` | `id` (matches `auth.users.id`) |
| `physics_simulations` | `id`, `topic_id`, `code_payload` |
| `chemistry_simulations` | `id`, `topic_id`, `code_payload` |
| `biology_simulations` | `id`, `topic_id`, `code_payload` |
| `mathematics_simulations` | `id`, `topic_id`, `code_payload` |

The per-subject simulation tables are addressed dynamically as
`` `${subjectName}_simulations` ``, so adding a subject in the admin panel implies
a matching table exists. `all_simulations` is the union view the panels read from.

### Missing table

`whatsapp_documents` **does not exist** in the hosted project. Requesting it
returns:

```text
PGRST205: Could not find the table 'public.whatsapp_documents' in the schema cache
```

Two queries in `student-panel/src/features/simulations/hooks/useWhatsAppSender.jsx`
(lines 89 and 101) read and write it, so the WhatsApp send feature is broken at
runtime. Decide whether to create the table or remove the feature; do not do
either without approval.

### Edge Functions in use

| Function | Called from |
| --- | --- |
| `chat-tutor` | both panels — streaming AI tutor and study-guide generation |
| `generate-simulation-prompt` | admin — wizard prompt builder |
| `suggest-requirements` | admin — requirement suggestions |
| `extract-html-details` | admin — metadata extraction from uploaded HTML |
| `send-whatsapp` | student — WhatsApp delivery |

Their source lives only in the hosted project until `functions download` is run.
Their secrets (AI provider keys, WhatsApp credentials) are set on the server and
must never appear in a panel or in this repository.

### Anonymous access observation

`all_simulations` returns rows to the anon role. `classes`, `subjects`, `topics`,
`admin_users`, and the per-subject simulation tables return none. That asymmetry
is worth reviewing once the real policies are pulled — simulation payloads being
world-readable while the curriculum tree is not may be deliberate, or may be a
policy gap.
